# Benchmark results: ModernLibs.FileHelpers 4.9.0 against 4.8.1

Recorded on 2026-11-09 (UTC) as an A/B run: the same benchmark suites, built from two copies of the
repository on the same virtual machine. Each suite ran for 4.8.1 and then for 4.9.0 before the next
suite started. The suites were split over two virtual machines of the same size; both versions of a
suite always ran on the same one.

| | Library code | VM 1 (22:27 to 23:21 UTC) | VM 2 (22:28 to 23:09 UTC) |
|---|---|---|---|
| 4.8.1 | `63e65e8` (`main`, tag `v4.8.1`) | `DelimitedComparison`, `FixedWidthComparison`, `QuotedFields`, `SepComparison`, `Write` | `AsyncStreaming`, `DelimitedParse`, `FixedWidthParse`, `OptimizedParse` |
| 4.9.0 | `39f287b` (`release/4.9.0`) | same | same |

The library code of the 4.9.0 release is the same as in `39f287b`: the other commits after it change
tests, benchmarks and documentation, or were reverted (a quote scanner change and a cap on pooled
record buffers). Both copies run the benchmark code of `08e54dc`, with the competitor versions below.

All suites except the parallel and multi-record write suites were run. For 4.8.0 against 4.8.1, see
[v4.8.1.md](v4.8.1.md); for the 4.8.0 baseline with the environment caveats, see [v4.8.0.md](v4.8.0.md).
Those runs used a different machine (AMD Ryzen 9 5900X under WSL2), so compare their times only
within each file.


## Reading the results

The FileHelpers 3.5.2, Sep, Sylvan, CsvHelper and `SliceAllFields_SpanSlicer` rows are controls: their
code is the same in both runs. They moved by between 4 % faster and 5 % slower, so treat a difference
of that size as noise. `WriteFile` writes through the same code in both versions and is also unchanged.
The CsvHelper rows are CsvHelper 34.0.0 with source-generated (`[CsvRecord]`) records; they are not
comparable with the CsvHelper 33.0.1 rows of [v4.8.0.md](v4.8.0.md) and [v4.8.1.md](v4.8.1.md), which
used reflection mapping.

**Each benchmark runs in a process of its own and its setup runs only its own correctness check**
(since `08e54dc`). Before, one setup per suite ran the check of every benchmark of the suite, so every
measured process had first read the file with FileHelpers. 4.9.0's `ReadFile` returns its record
buffers to `ArrayPool<T>.Shared`, and the pooled arrays that stay alive change when the garbage
collector runs: in an earlier run the `SliceAllFields_SpanSlicer` control was up to 53 % slower in the
4.9.0 process, and renting and returning the same array sizes in a 4.8.1 process made it as slow. That
setup also affected the competitor rows of earlier runs.

## Summary

- **`ReadFile(path)` to an array is 28 to 52 % faster and allocates about 60 % less.** It parses the
  records as it reads the input instead of loading it into one string first; `ReadStream(reader)` uses
  the same path. At 100K rows of the 25-column file, `ReadFile` takes about 154 ms instead of 216 to
  243 ms and allocates 75.7 MB instead of 186 MB, about the same as `ReadString` of the text, Sep and
  Sylvan.
- **Dates with a fixed-width invariant format are parsed in place.** Formats such as `yyyy-MM-dd`,
  `ddMMyyyy` or `s` no longer go through `DateTime.TryParseExact` (which is still used for every other
  format and as a fallback). The benchmark records have two such dates per row: `ReadString` and
  `ReadSpan` to an array are 17 to 31 % faster and the callback reads 31 to 40 % faster. These numbers
  combine all changes of the release: the `ReadString` and `ReadSpan` callbacks also skip a line count
  pass, and `ReadFile` with a callback, which does not, is 31 to 37 % faster. `ReadString` with a callback at 100K rows: 64 ms instead of
  102 ms. Allocation is unchanged.
- **Quoted fields: 27 to 44 % faster with about half the allocation.** The file read streams, a quoted record
  that fits on one line is scanned once instead of twice, and the quote scan skips lines without a
  quote and jumps between delimiter and quote positions with vector search. 100K rows: 46 ms instead of
  64 ms.
- **Fixed-width reads allocate 43 to 45 % less.** Class records are 17 to 43 % faster. Struct records
  are 11 to 14 % faster at 10K rows and 14 % slower at 100K rows (50 to 51 ms instead of 44 to 45 ms),
  the same in both fixed-width suites.
- **`WriteString` is 17 to 30 % faster and allocates about 50 % less at 10K and 100K rows and 46 %
  less at 1M rows.** It collects the text in pooled chunks and builds the result string once. 1M rows:
  819 to 837 ms instead of 1,080 to 1,093 ms.
- **The multi-record `ReadAsync` is between 1 % slower and 11 % faster.** The multi-record
  `ReadFile` (`ReadSync`) is 5 % faster at 10K rows and 7 % slower at 100K rows; the 7 % is a little
  more than the controls moved.
- **`WriteFile` is unchanged.**

Against the other libraries in this run: the 25-column read to an array is faster than Sep and
CsvHelper 34 at every size (100K rows: 155 ms, Sep 171 ms, CsvHelper 165 ms) and slower than Sylvan
at 10K and 100K rows (8.1 ms against 6.1 ms; 155 ms against 131 ms); at 1M rows both take 1.45 s.
`WriteString` is 22 to 33 % faster than Sep (100K rows: 69 to 70 ms, Sep 102 ms) and 15 to 22 % slower
than CsvHelper 34 (100K rows: 58 ms). Sep, Sylvan and CsvHelper still read the quoted file faster
(100K rows: 46 ms, Sep 29 ms, CsvHelper 28 ms, Sylvan 38 ms). The fixed-width class read is faster
than CsvHelper 34 (100K rows: 48 to 51 ms, CsvHelper 54 ms) and twice as fast as FileHelpers 3.5.2
(111 ms).
