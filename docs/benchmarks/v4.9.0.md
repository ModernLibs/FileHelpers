# Benchmark results: ModernLibs.FileHelpers 4.9.0 against 4.8.1

Recorded on 2026-11-08 and 2026-11-09 as an A/B run: the same benchmark suites, built from two clones of
the repository on the same machine, one directly after the other.

| | Commit | Run |
|---|---|---|
| 4.8.1 | `63e65e8` (`main`, tag `v4.8.1`) | 23:21 to 00:12 |
| 4.9.0 | `d9c1ea6` (`release/4.9.0`) | 00:12 to 00:55 |

The 4.9.0 run was made before the last commit of the release (`62fcab0`). That commit only changes
error paths (a reader that fails while a failed read drains it, a write that fails to close) and adds
tests; no benchmark runs that code.

All nine suites of the benchmark project were run. None of them covers the multi-record write or a
`ConverterBase` field; 4.9.0 also changes those (see the CHANGELOG), and their allocation is checked by
tests instead. For 4.8.0 against 4.8.1, see
[v4.8.1.md](v4.8.1.md); for the 4.8.0 baseline with the environment caveats, see [v4.8.0.md](v4.8.0.md).

## Reading the results

The FileHelpers 3.5.2, Sep, Sylvan, CsvHelper and `SliceAllFields_SpanSlicer` rows are controls: their
code is the same in both runs. Most of them moved by between 8 % faster and 3 % slower, so treat a
difference of that size as noise. Two control cells moved much more: CsvHelper on the quoted file at
100K rows (+33 %) and `SliceAllFields_SpanSlicer` at 100K rows (+50 %). A single cell can therefore be
off by more than that; the 4.9.0 gains below hold across row counts and suites.

## Summary

- **`ReadFile(path)` to an array is 29 to 56 % faster and allocates 2.5 times less.** It parses the
  records as it reads the file instead of loading the file into one string first (`ReadStream(reader)`
  now reads the same way).
  At 100K rows of the 25-column file, `ReadFile` takes 119 ms instead of 187 ms and allocates 75.7 MB
  instead of 186 MB: the same as `ReadString` of the text, and the same as Sep and Sylvan.
- **Dates with a fixed-width invariant format are parsed in place.** Formats such as `yyyy-MM-dd`,
  `ddMMyyyy` or `s` no longer go through `DateTime.TryParseExact` (which is still used for every other
  format and as a fallback). The benchmark records have two such dates per row: `ReadString` and
  `ReadSpan` to an array are 18 to 32 % faster. The callback reads, which also skip a line count pass
  when the record has no `[IgnoreLast]`, are 32 to 39 % faster (`ReadString` with a callback at 100K
  rows: 47 ms instead of 76 ms). Allocation is unchanged.
- **Quoted fields:** 23 to 37 % faster with half the allocation (the file read streams; a quoted record
  is scanned once instead of twice).
- **Fixed-width reads:** class records 18 to 46 % faster, struct records 10 to 22 % faster with one
  exception (`FixedWidthParse`, struct, 100K rows: +2.9 %, against -21.5 % for the same read in
  `FixedWidthComparison`). Both allocate about 44 % less.
- **`WriteString` is 17 to 40 % faster and allocates half as much.** It collects the text in pooled
  chunks and builds the result string once. 1M rows: 504 to 628 ms instead of 817 to 844 ms.
- **`ReadAsync` of a file is 22 to 30 % faster** (asynchronous file stream, 16 KB pipe reads).
- **`WriteFile` and `ReadSync` are unchanged** (within noise).

Against the other libraries, in these runs: the 25-column read to an array is now slightly faster
than Sep (100K rows: 114 ms, Sep 128 ms) and within 10 % of Sylvan (120 ms, Sylvan 110 ms); `WriteString` is
faster than Sep (100K rows: 50 ms, Sep 80 ms). Sep and Sylvan still read the quoted file faster
(100K rows: 38 ms, Sep 22 ms, Sylvan 29 ms).
