# Benchmark results: ModernLibs.FileHelpers 4.8.0

Recorded on 2026-10-20 with the benchmark code at commit `5ceee94` (branch `v4.8`), the first run after
the benchmarks were fixed to parse their data correctly (see [Correctness](#correctness)). Numbers from
earlier milestones, including [v4.0.0.md](v4.0.0.md), are not comparable with these.

## Environment

| | |
|---|---|
| CPU | AMD Ryzen 9 5900X 4.50 GHz, 12 cores / 24 logical processors |
| OS | Ubuntu 26.04.1 LTS under **WSL2** on Windows 11 (kernel 6.18.33.2-microsoft-standard-WSL2) |
| .NET | SDK 10.0.113, runtime 10.0.13, X64 RyuJIT x86-64-v3 (AVX2), Concurrent Workstation GC |
| BenchmarkDotNet | 0.15.8, **default job** (BenchmarkDotNet chooses warmup and 15 to 100 measured iterations per benchmark), `--memory` |
| Competitors | FileHelpers 3.5.2, Sep 0.14.1, Sylvan.Data.Csv 1.4.0, CsvHelper 33.0.1 (pinned in `Directory.Packages.props`) |

The machine ran nothing else during the runs. BenchmarkDotNet could not raise the process priority
(no permission under WSL2), and every benchmark ran on the same runtime (10.0.13). The two runs below
took 21 min 38 s and 19 min 49 s.

## Commands

Run from the repository root:

```bash
# Comparison suites (published below)
dotnet run -c Release --project benchmarks/ModernLibs.FileHelpers.Benchmarks -- \
  --filter "*DelimitedComparisonBenchmarks*" "*FixedWidthComparisonBenchmarks*" "*QuotedFieldsBenchmarks*" \
           "*SepComparisonBenchmarks*" "*WriteBenchmarks*" "*AsyncStreamingBenchmarks*" \
  --memory --exporters github --artifacts BenchmarkDotNet.Artifacts/main

# Remaining suites
dotnet run -c Release --no-build --project benchmarks/ModernLibs.FileHelpers.Benchmarks -- \
  --filter "*DelimitedParseBenchmarks*" "*FixedWidthParseBenchmarks*" "*OptimizedParseBenchmarks*" \
  --memory --exporters github --artifacts BenchmarkDotNet.Artifacts/extra
```

The tables below are the `*-report-github.md` files BenchmarkDotNet wrote, without their environment
header (it is the one above).

## Summary

**Against FileHelpers 3.5.2** (same record layouts, same attributes, same text):

- Reading the 25-column delimited file into an array is **1.9 to 2.2 times faster** in 4.8 and allocates
  about 20 % less (100K rows: 182 ms and 186 MB against 344 ms and 231 MB).
- Reading the 80-character fixed-width file is **1.6 to 2.1 times faster** with a class record
  (100K rows: 53 ms against 84 ms), but 3.x allocates 14 to 16 % less here (59 MB against 71 MB).

**Against the CSV libraries** (each library parses the same file into objects with the same 25 typed
properties):

- **Sep and Sylvan read faster than 4.8.** For the 25-column file at 100K rows: Sylvan 107 ms, Sep 122 ms,
  ModernLibs.FileHelpers 185 to 191 ms, CsvHelper 352 ms. The gap narrows with size (Sep is 2.1 times
  faster at 10K rows, 1.3 times at 1M). For the quoted-fields file at 100K rows: Sep 22 ms, Sylvan 28 ms,
  ModernLibs.FileHelpers 49 ms, CsvHelper 78 ms.
- **CsvHelper is slower than 4.8** on every read and write measured here: 1.6 to 2.2 times on reads and
  2.1 to 3.2 times on writes.
- **Writing is on par with Sep.** `WriteString` of 100K records takes 70 ms, Sep 75 ms (both write the
  same text, header included), CsvHelper 173 ms. `WriteFile` streams to disk with about 10 KB allocated
  whatever the row count.
- **`ReadFile` to an array allocates about 2.5 times more than Sep or Sylvan** (186 MB against 76 MB for
  100K rows). `ReadFile(path)` loads the whole file into one string before parsing; the records
  themselves cost the same as the competitors' (`ReadString` and the streaming callback reads allocate
  75 MB, the same as Sep). `ReadFile(path, callback)` streams the file and is about twice as fast as
  `ReadFile(path)` at 100K rows (99 ms against 198 ms), because it neither loads the whole file nor keeps
  every record alive through the garbage collections.

**Allocation and struct records.** None of these datasets has a record made only of value types:
every record has string fields, and the strings dominate allocation (a fixed-width struct record
allocates 97 % of what the class record does). The zero-allocation read of struct records with
value-type fields is checked by the test suite, not measured here. Struct records were 1.4 times
slower than class records at 10K rows and 8 to 26 % faster at 100K rows (fixed-width suites).

**Async.** `MultiRecordAsyncEngine.ReadAsync` takes 1.4 times as long as the synchronous
`MultiRecordEngine.ReadFile` at 10K rows and is within 6 % of it at 100K rows. It allocates 24 to 29 %
less because it does not build the result array. The cancellable variant was slightly faster than the
plain one at 100K rows (33.0 ms against 35.1 ms); treat that difference as noise between processes.

**Caveats.**

- WSL2 adds a virtualisation layer and BenchmarkDotNet could not raise the priority; absolute times on
  native Linux or Windows will differ. The ratios between libraries measured in the same run are the
  useful part.
- The CSV readers are measured with the row-to-object code written in each benchmark (by column index
  for Sep and Sylvan, `GetRecords<T>` for CsvHelper). FileHelpers additionally runs its record pipeline
  (converters, null-value and error handling, events). Dates are parsed by exact format in FileHelpers
  (`[FieldConverter(ConverterKind.Date, "s")]`) and by each CSV library's default invariant `DateTime`
  parser.
- `ReadFirstColumn_*` is not like-for-like: Sylvan and CsvHelper parse only the first column, while
  FileHelpers has no column projection and parses whole records.
- The 1M-row results include several Gen2 collections; they depend on the GC mode (Concurrent
  Workstation here).

## Correctness

Before 4.8.0 a failed conversion silently became `default`, and the benchmark records did not match
their data: the header line was read as a record, the generated dates did not match the converter
format, quoted fields were not unquoted, and the record types meant for FileHelpers 3.x resolved to
ModernLibs.FileHelpers (inside the `ModernLibs.FileHelpers.*` namespaces `FileHelpers.` names this
library), so the 3.x comparison measured 4.x against itself. Sep was also read without `Unescape`, so
its quoted-field results returned the raw quoted text.

The benchmarks now skip the header (`[IgnoreFirst]`), parse ISO 8601 dates with an explicit format,
quote-aware text fields (`[FieldQuoted]`, Sep `Unescape = true`) and name the 3.x package through a
`global::` alias. The datasets are a pure function of their row count (fixed seed, fixed base date).
Every `[GlobalSetup]` runs each benchmark method once and compares its rows (count and sampled fields)
or its written text (every line) with the raw dataset, and throws on any difference, so a benchmark
cannot silently measure wrong results again.
