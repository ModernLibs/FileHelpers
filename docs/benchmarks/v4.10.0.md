# ModernLibs.FileHelpers 4.10.0 benchmarks

This page records the Azure benchmark rounds of 4.10: the gates of the plan, 4.10 against the 4.9.1 package per VM and
runtime, runtime async on against off, and the library comparison. Every number names its round and VM and comes from
the raw files under [`raw/`](raw/README.md) (or, for the Gen0 / Gen1 / Gen2 and allocation columns, from the `*.runs`
folders of the archives that `raw/README.md` lists). No number on this page comes from a developer machine.

**What ships.** The `net11.0` asset of the package is compiled with runtime async on: the `net11-ra-on` columns are what
a .NET 11 application gets. `net11-ra-off` is the same commit built with `-p:FileHelpersRuntimeAsync=false`; it is
measured to show what runtime async changes, and it does not ship. Every scenario table shows both; the component
benchmarks (two methods of one build) and the `# noavx2` block run on `net10` and `net11-ra-on` only, by the lead's
ruling on D6: they measure code shapes that runtime async does not change.

## How to read this page

- **Ratios** are B/A, the ratio of the medians of the per-launch medians, with the 99.9 % bootstrap interval in
  brackets. Below 1.0 the second build is faster. "4.10 / 4.9.1" is the 4.10 build against the published 4.9.1 package
  on the same runtime (pairs `v410-net10`: `pkg-net10` -> `net10`; `v410-net11`: `pkg-net11` -> `net11-ra-on`). The
  4.9.1 package has no `net11.0` asset, so on .NET 11 it runs its `net10.0` library.
- **Rule B4.** A change counts when the 99.9 % interval excludes 1.0 and the median ratio differs from 1.0 by at least 3
  %. A claim holds when it holds on the reference VM `fh-amd` and on `fh-intel`. A claim about a hardware class that
  only one VM has (AVX-512 on `fh-intel`) holds by the same test on that VM alone. Verdicts: `faster`, `slower`,
  `no-change`.
- **Noise floor (owner, 2026-11-20).** A slowdown of up to 3 % against 4.9.1 is noise, not a regression. Such lines are
  named on this page (section "Lines within 3 %") and not called regressions. Every line slower by more than 3 % is in
  "Lines above 3 % slower".
- **Rounds.** Each A/B round runs 7 launches per side, A and B interleaved, BenchmarkDotNet default job with at most 20
  iterations; the rounds after Step 0 also cap the row count at 100K (`--max-rows 100000`). The library comparison runs
  3 launches per configuration and is not an A/B.
- **Hardware.** `fh-amd` is an Azure `Standard_D4ads_v5` (4 vCPUs, AVX2), `fh-intel` a `Standard_D4ds_v5` (4 vCPUs,
  Intel Xeon Platinum 8370C, AVX2 and AVX-512), both Spot, Poland Central, Ubuntu 24.04, SDK 11.0.100, .NET 10.0.15 and
  11.0.0. The Spot VMs were evicted and restarted during the rounds, and `fh-amd` came back on a different host CPU (AMD
  EPYC 9V74 or AMD EPYC 7763, column CPU below). Every result file was measured on one CPU from its first to its last
  launch (BenchmarkDotNet's `ProcessorName` in each launch's report), so every ratio is a same-hardware ratio; times of
  different rounds on `fh-amd` are not compared with each other on this page. Host CPU of `fh-amd` per round (the `Model
  name` line of `lscpu` in each round's `machine.txt`, written at the round's start): `step0` EPYC 7763, `g1` EPYC 9V74,
  `simd` EPYC 9V74, `recheck` EPYC 9V74 (the VM came back on an EPYC 7763 after the eviction of 2026-11-18, which
  `machine.txt` does not record; 24 of its 29 result files report EPYC 7763 in BenchmarkDotNet's `ProcessorName`; the
  five 9V74 files are `sdk-net10` and `sdk-net11` of the multi-record write and `v410-net10` of `Engine_ReadAsync_Path`,
  `Engine_ReadFileAsync_Callback` and `ReadFileAsync_Callback_ProcessAndDiscard`, so in the results and times rows of
  the last two lines the `net10` and `net11` columns come from different host CPUs), `write` EPYC 7763, `noavx2` EPYC
  7763, `diagAS2` EPYC 7763, `diagFW2` EPYC 7763, `r3cmp` EPYC 9V74, `r3q` EPYC 9V74. `fh-intel` is a Xeon Platinum
  8370C in every round.
- **Reproducing.** `python3 -I benchmarks/tools/round-report.py docs/benchmarks/raw/<round>` prints the full tables of a
  round (`--compare` for `r3cmp-2026-11-19` and `r3q-2026-11-20`). The tables of a method against another method of the
  same build (the tokenizer loops, call shapes, slice shapes) use `round-report.py`'s `compare_methods`, the same
  comparison its "Coding-pattern choices" table prints.

## Lines above 3 % slower

Against 4.9.1, one line of the judging rounds (the round named in the tables below) is slower by more than 3 %: the
Native AOT read with `DisableVectorizedTokenizer` set on .NET 11 (item 4, accepted by the owner). No other line is. The
gates and selections above that are above 3 % in the wrong direction, and the owner's decision on each (2026-11-21
unless noted):

1. **Goal 1, `ReadFile` at 100K rows on `fh-intel`:** 0.963 (`net10`) and 0.996 (`net11-ra-on`), round `simd`; the
   target is 0.95. It is faster than or level with 4.9.1, and at 10K rows both runtimes meet it (0.831, 0.838). At 100K
   rows the read keeps every record alive: 75.66 MB allocated per read and 1000 Gen2 collections per 1,000 reads in both
   builds (GC table), the same as 4.9.1. **Target not met, accepted by the owner; not slower than 4.9.1.**
2. **Goal 3, quoted `WriteString`:** 0.784 to 0.836 against the target 0.50, round `write` (faster than 4.9.1 on both
   VMs and runtimes, by 16 to 22 %). **Target not met, accepted by the owner; not slower than 4.9.1.**
3. **F1, fixed-width `WriteString` at 10K rows on `fh-intel`:** `net11-ra-on` 1.054 [1.016, 1.081] times the `net10`
   time, round `write`, before `WritePadded` (on `fh-amd` the same pair reads 1.215 [0.954, 1.331] at 10K and 1.050
   [0.988, 1.073] at 100K, both no-change). Against 4.9.1 the same line is 0.704 (`net10`) and 0.633 (`net11-ra-on`) in
   `diagFW2`, after `WritePadded`. **Target not met, accepted by the owner; not slower than 4.9.1.**
4. **AOT `PackageAssets_ParseAndDiscard_NoVector` on .NET 11:** 1.088 [1.078, 1.097] (`fh-amd`) and 1.059 [1.030, 1.064]
   (`fh-intel`) times 4.9.1, round `simd`. This is the read with the `DisableVectorizedTokenizer` switch set; the
   default AOT read is 0.964 and 0.984 times 4.9.1. **Accepted by the owner (2026-11-19)**, documented under
   "Tradeoffs".

## Tradeoffs

- **Native AOT, `DisableVectorizedTokenizer` on .NET 11.** With the switch set, the AOT read on .NET 11 is 1.088
  (`fh-amd`) and 1.059 (`fh-intel`) times 4.9.1 (round `simd`). The default AOT read is 0.964 and 0.984 times 4.9.1, and
  on .NET 10 the switch read is faster than 4.9.1 (0.815, 0.923). The owner accepted this on 2026-11-19.
- **Fixed-width write, `WritePadded`** (commit `111ac6f`; Azure evidence: round `diagFW2-2026-11-19`). 4.10 adds the
  hidden member `RecordWriter.WritePadded` (T22 freeze Revision 2) so that the generated fixed-length `Format` makes one
  call per padded string field. Without it, fixed-width `WriteString` on `net10` was slower than 4.9.1 in three of its
  four rows of round 2 (1.077 to 1.217, round `write`). With it, fixed-width `WriteString` is 0.647 to 0.798 times 4.9.1
  on `net10` and 0.337 to 0.726 on `net11-ra-on` (round `diagFW2`).
- **64 KB pipe reads** (commit `7a77977`; Azure evidence: round `diagAS2-2026-11-19`). `ReadAsync(path)` and the other
  pipe-based reads now read 64 KB per stream read instead of 16 KB (`FileBuffers.PipeReadSize`). Round 2 had
  `Engine_ReadAsync_Path` 1.044 and `_ExceptionEvery100` 1.054 and 1.088 times 4.9.1 on `fh-intel` `net10`; with 64 KB
  reads they are 0.738, 0.745 and 0.764 (`diagAS2`). The allocation of the read is unchanged within 0.5 % (75.32 MB with
  4.9.1, 74.97 MB with 4.10, 100K rows). A reader who compares round-2 async numbers with these should know the read
  size changed between them.
